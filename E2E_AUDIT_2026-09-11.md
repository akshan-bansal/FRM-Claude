## 2. Findings

### F1 — HIGH · Overlay risk clauses are silently dropped from the card thesis

`src/trading_live_claude/intel/vs_engine.py:190-196`, `_compose_thesis` at `:322-338`

The thesis is the only market context a human sees before tapping ACCEPT. Under
truncation, the **geopolitical / energy / fear-greed risk clause is the first thing
discarded.**

`explain()` assembles clauses as `core → overlay → notes`, then `_compose_thesis` pops
from the **end** until the string fits 140 chars. Overlay sits behind all six core
clauses, so it goes first — while cosmetic core clauses survive.

Measured, with `strategic_risk=85, energy_stress=0.80, fear_greed=20`:

```
[0] len= 37  BTC/USD — momentum signal (long side)
[1] len=  9  rank 2/50
[2] len=  5  R=2.1
[3] len= 14  trend +1.20%/d
[4] len= 24  RSI 72 (overbought zone)
[5] len=  8  ATR 2.5%
[6] len= 39  geo-risk 85; energy stress high; F&G 20   <-- DROPPED

joined = 148 chars (8 over budget)

ACTUAL thesis (107 chars):
  BTC/USD — momentum signal (long side); rank 2/50; R=2.1; trend +1.20%/d; RSI 72 (overbought zone); ATR 2.5%
```

Being 8 characters over budget costs the user a 39-character extreme-risk warning, while
`ATR 2.5%` (8 chars) is retained. The trader sees a clean momentum thesis and approves
a trade during a severe-risk regime with **no indication on the card.**

The overlay data *is* persisted correctly to the writeup (`overlay_snapshot` is intact),
so this is purely a presentation-ordering defect — but the writeup lives behind a CENTER
button whose detail view is still `TODO` in firmware (`main.c:483`). In practice the
warning reaches nobody.

This contradicts `CLAUDE.md:121-122` ("overlay risk clauses have priority over
user-supplied notes during truncation") and the code's own comment at `:190-191`
("Risk signals must never be truncated in favor of user-supplied notes"). Strictly read,
that promise is about *notes* and is kept — but the docstring's stated priority ordering
and the test both expect risk to outrank the droppable core tail.

**Fix:** promote the overlay clause to index 1, immediately after the headline. Verified
— every clause then fits in 138 chars with nothing dropped:

```
BTC/USD — momentum signal (long side); geo-risk 85; energy stress high; F&G 20; rank 2/50; R=2.1; trend +1.20%/d; RSI 72 (overbought zone)
```

Caught by `test_thesis_generation_with_overlay_stress` — a correct test that found a
real bug and has been failing since it was committed.

### F3 — HIGH · The documented canonical wire format is not the implemented one

`E2E_TEST_RESULTS.md:65-66` vs `src/trading_live_claude/execution/approval.py:76-87`

```
documented:  ib|BUY|ETH/USD|5|2000.00|10000.00|500.00|76bfb63f67ef      (8 fields)
implemented: broker|action|symbol|shares|entry(.4f)|notional(.2f)|account|intent_id|nonce   (9 fields)
```

Divergences: entry precision `.2f` vs `.4f`; the document carries `risk_dollars`, the
implementation does not; the implementation carries `account` and **`nonce`**, the
document carries neither.

`nonce` is the replay-protection field. Anyone implementing a card against the documented
format ships without replay protection and produces signatures that can never verify.
The documented string is `MockPrompt.from_intent`'s format (`test_e2e_isolated.py:75`) —
the mock's wire contract was transcribed into the results document as if it were the
system's.

### F4 — HIGH (security) · The card signs opaque server bytes; WYSIWYS is not enforced on-device

`firmware/tradecard/main/main.c:445-449`, `:466-478`

`canonical_bytes()` documents itself as *"WYSIWYS: every field a user cares about is in
here"* (`approval.py:70`). The fields are indeed in the canonical string — but the card
never checks that the string it **signs** describes the trade it **displayed**.

```c
render_prompt(p);                    /* renders from JSON symbol/action/shares/notional_usd */
...
sign_and_respond(id, canon, 1);      /* signs the separate opaque "canonical" JSON string */
```

`render_prompt` reads `symbol`, `action`, `shares`, `notional_usd` as individual JSON
fields. `sign_and_respond` signs `canonical` verbatim. Nothing reconciles the two.

A compromised or simply buggy shim can render `BUY XIC.TO 10sh $310` while supplying
canonical bytes for `BUY TSLA 500sh $100000`. The user approves what they see and
cryptographically signs what they cannot. The server then verifies that signature
successfully — it matches the canonical it issued — and dispatches the hidden order.

The card exists to be an independent gate against exactly this host-compromise scenario.
As built, it attests to a string the host chose rather than to the trade the human read.

**Fix:** the card must rebuild the canonical string from its rendered fields and
`sodium_memcmp` it against the supplied one, refusing to sign on mismatch. This also
turns F3 from a latent documentation issue into a caught error.

### F5 — MEDIUM · Single-consumption of a prompt is not atomic

`approval.py:399-426` · `approval_sqlite.py` `respond()`

Both stores check `consumed`/`verdict` under the lock, **release the lock** to verify the
signature, then re-acquire and write the verdict **without re-checking**. Two concurrent
valid responses can both pass the guard.

- **InMemory** has no compare-and-swap. Last writer wins: a DECLINE can be overwritten by
  a concurrently-arriving ACCEPT, and two passbook entries are appended for one intent.
  The class docstring's promise that it "never trusts a response for an intent that has
  … already been consumed" is not held atomically.
- **SQLite** is protected — its `UPDATE … WHERE intent_id = ? AND verdict IS NULL` is a
  proper CAS, so the verdict itself is safe. But it `return True` unconditionally without
  inspecting `rowcount`, so the losing responder is told its DECLINE succeeded when the
  ACCEPT had already won.

**Empirical note, stated plainly:** I could not reproduce the InMemory verdict flip in 300
barrier-synchronized trials — CPython's GIL keeps the window between the two critical
sections very small. This is a structural defect visible by inspection, not an observed
failure. The realistic trigger is a slower `verify()` (the SQLite-backed registry does
disk I/O) or a free-threaded build. The SQLite `rowcount` bug, by contrast, fires
deterministically whenever two responses race.

**Fix:** re-check `consumed`/`verdict` inside the second `with self._lock` (InMemory);
return `cursor.rowcount == 1` (SQLite).

## 3. What is in good shape

Worth stating, because the defects above are concentrated in the test and presentation
layers rather than the core:

- **Gate ordering is correct.** `ApprovalRouter.submit` runs `Router._gate` *before*
  publishing any prompt, so the user is never asked to approve something the router would
  refuse. Verified passing.
- **Gate re-run after approval.** `approval.py:545` re-submits through the full router
  after ACCEPT, closing the window where heat or the kill-switch changed while the user
  was deciding.
- **Autonomous incompatibility is enforced at construction** (`:470-474`), matching the
  documented rule that card approval and `AUTONOMOUS_ENABLED` are mutually exclusive.
- **Shim auth is done properly** — Bearer token compared with `hmac.compare_digest`
  (`approval_asgi.py:268`), consistent 401s, `BearerAuth` advertised in the OpenAPI schema.
- **Narrator failure is correctly non-fatal** — `thesis_fn` exceptions are swallowed and
  the prompt publishes with empty intel fields (`:520-524`).
- **Signature rejection does not consume the prompt** (`:415`), so a genuine card can still
  respond after a forged attempt.
- **887 passing tests at 77% line coverage** across the wider framework.

### Defects found while fixing

**F11 — HIGH · The physical card could not authenticate.** Every `/v1` route requires the
Bearer token, `wire_card_approval` mints one by default, and the firmware never sent an
`Authorization` header — so register, poll and respond would all return 401. Added
`TRADECARD_SHIM_TOKEN` to menuconfig, sent on every request, with an explicit log on 401.

**F12 — MEDIUM · Pending prompts silently dropped on the card.** A 4 KB receive buffer
overflowed at roughly five queued prompts; the truncated JSON failed to parse and the card
showed nothing while prompts expired. Buffer raised to 16 KB and truncation now logs.

**F13 — HIGH · Fractional crypto quantities were misrepresented.** The router passes
fractional sizes through to the broker, but `canonical_bytes()` did `str(int(shares))`, so
the card signed **`0`** shares for a 0.05 BTC order. Separately, `KrakenBroker.place_order`
sent `str(float)`, which produces `"volume": "5e-08"` for 5 satoshi — scientific notation
Kraken's API does not accept. A shared `brokers.models.plain_decimal()` now emits exact
decimal text (`0.00000005`, and `0.000000005` without rounding up or collapsing to zero)
for the signed canonical and for Kraken `volume` / `price` / `price2`. Whole quantities keep
the historical `12` form, so existing equity signatures are byte-identical.

### Correction to F4's framing

In the default deployment the shim runs as a thread inside the same process as the router
and broker credentials. A *compromised* shim there already controls the host and can place
orders without the card at all, so F4 does not defend against that. What the fix does
defend against is the link the card actually uses: plain HTTP on the LAN, where an attacker
could rewrite display fields in transit. They cannot rewrite `canonical` without the
signature failing server-side, and the card no longer shows anything that isn't in
`canonical`. It also catches honest shim bugs that would render the wrong trade.

**Not verified:** the firmware changes are written but **not compiled** — no ESP-IDF or C
compiler on this machine. Run `idf.py build` before flashing. The same logic in the Python
simulator is tested.

## 7. Open decisions (not changed — each is a design or risk-policy call)

1. **The thesis is not signed.** On the plain-HTTP LAN link, a man-in-the-middle can strip or
   rewrite the risk text (the very clauses F1 restored) without breaking the signature.
   Options: TLS with a pinned shim certificate (already a README TODO), or add a thesis hash to
   `canonical` (a protocol change that requires reflashing every card).
2. **Stop-loss, target and risk dollars are neither displayed nor signed.** The user approves a
   trade without seeing where the stop is.
3. **Leverage-cap trimming floors crypto to zero.** `router.py:293` computes
   `int(fit_notional // intent.entry)`, so when the gross-leverage cap trims a BTC order it
   rounds to 0 and rejects instead of resizing. This is risk-gate behaviour, so it was left
   untouched.
4. **No lot-size quantization before the intent.** Sizing can produce sub-satoshi quantities.
   The card now shows them faithfully, but Kraken will reject them. Quantize to each pair's lot
   decimals in the sizer.
5. **The bearer token sits in firmware flash as plain text.** Enable ESP32-S3 flash encryption
   before a card leaves the bench.
6. **`feat/tradecard-approval`** (worktree `FRM-Claude-tradecard`) is 12 commits behind this
   branch and has none of these fixes. If a PR is open from it, it ships the defects above.
